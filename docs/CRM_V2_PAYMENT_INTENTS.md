# CRM v2 — full settlement from Sheets and Calendar (2026-11-25)

## Delivered
- CrmPaymentIntents.gs consumes the explicit "Отметить оплату" marker in Аренды column K and "Оплата: Отметить оплату" in the private managed Calendar event description. Read-only status text is not an instruction. Both sources settle only the remaining balance of a confirmed, converged booking with a current accepted quote. Existing Telegram receipts count toward that balance.
- The same deterministic SHA-256 receipt ID per booking/revision prevents duplicate full-settlement receipts across Sheet and Calendar, including a lost response. Acknowledgement clears only the Sheet action cell; Calendar status is updated by ETag-guarded description-only patch. No fabricated receipt for zero quotes. An already-used settlement ID after a refund requires explicit payment rather than automatic recharge.
- Calendar snapshot parsing supports the original two-line format and an optional recognized payment line; booking writes preserve read-only payment text. Active payment instructions block Calendar mutation until resolved. Unknown text, unsynchronized booking, stale quote and unauthorized deployment remain fail-closed.
- TEST pass runs payment processing after booking reconciliation and first finance projection, with explicit CRM_V2_PAYMENT_INTENTS_TEST_ENABLED=true in addition to existing TEST write flag. It refreshes Sheet finance after new receipts. Telegram payments reach Calendar on the next reconciliation. Reports include receipts, review/errors and limits.
- Tests exercise simultaneous markers, existing partial Telegram payment, ambiguous append, conditional acknowledgement failure, stale quote, read-only status, non-billable zero quote and refund retry guard.

## Limitations and next
- Sheet/Calendar marker means full remaining balance only, not arbitrary amount or refund. Partial receipts remain Telegram operations. The calendar description still includes existing technical JSON and one readable payment line. It is not yet a completely human-readable editing interface. The marker is processed by reconciliation, not instantaneous.
- Trusted Sheet/Calendar source is recorded, not an inferred individual editor identity. Strict protections and actual live permissions are release gates. External UI can bypass ScriptLock; rechecks and ETag guards reduce risk but do not provide cross-service atomicity. Concurrent edit of booking and payment may require clearing/re-entering the marker after price review. Post-refund reuse of a consumed marker on the same revision is intentionally blocked; use explicit Telegram payment.
- No native GAS deployment, triggers, real Calendar or ledger writes performed. All tests use simulated services. Code/test commit 30cdba7c25857d058a6dfc9b5ebf01005be05d77; CI evidence tracked in PR.
- Remaining: managed title edits, explicit quote review, actionable diagnostics/protection, backup/restore, migration and live acceptance.
