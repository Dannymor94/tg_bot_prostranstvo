## Backup implementation
CrmBackup.gs creates a native spreadsheet copy, full Calendar REST event metadata (including cancelled events and recurring series), and allowlisted operational state for pending/replayed Telegram commands and outbox/offset. Credentials, binding, admin configuration and UI sessions are excluded. The archive is written to an explicitly configured owner-only private Drive folder. The manifest is written last; verifies distinct IDs, folder membership, workbook shape and SHA-256 content hash, event bundle checksum, event count and source binding. The source is reread for changes around copying; this detects changes but is not a cross-service atomic snapshot. Existing valid daily backup is reused. Partial failed backups are left for operator review, not blindly deleted.

Manual TEST activation: set CRM_V2_BACKUP_FOLDER_ID to a private owner-only folder; CRM_V2_BACKUP_TEST_ENABLED=true in the isolated project; run crmV2BackupTest. Verify using crmV2VerifyBackupTest. For a separate workbook restore rehearsal set CRM_V2_RESTORE_TEST_ENABLED=true and run crmV2RestoreWorkbookTest. Restore creates a new copy, verifies content and reads accepted state, ledger, journal, settings and tenant directory; never overwrites an active workbook. Calendar bundle is verified but not reimported by this procedure. No automatic state/credential restoration.

Retention planner keeps the 14 newest available daily dates plus one latest backup for each of the 12 newest available months. Automatic scheduling, deletion of verified expired backup sets, Calendar restore replay, operational-state restore and actual live backup/restore drill remain release gates. No automatic deletion enabled.
